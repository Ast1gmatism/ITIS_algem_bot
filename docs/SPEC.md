# Алгем: спецификация продукта

**Версия:** 0.2.  
**Дата фиксации:** 19 ноября 2026 года.  
**Статус:** обновлено по ответам на контрольные вопросы; реализация не начата.

Связанные документы: [решения](DECISIONS.md), [технические заметки](IMPLEMENTATION_NOTES.md).

## 1. Главная цель

Облегчить студентам занятие номеров, убрать связанный с этим шум в общем чате и облегчить работу ответственных на занятии.

Ответственному не должно быть нужно одновременно:

- восстанавливать по переписке, кто какой подпункт занял;
- расшифровывать Telegram-псевдонимы;
- искать человека в таблице, чтобы понять его выходы, баллы и приоритет;
- вручную переносить подтверждённые выходы и пересчитывать результаты.

**Основной сценарий:** добавили номера → студенты заняли их кнопками → ответственный видит очередь и показатели → подтверждает реальную сдачу → бот обновляет учёт и ведомость.

**Две рабочие зоны:** табло бронирования в общем чате и админ-панель в личном чате с ботом. Таблица не нужна как второй экран для обычного подтверждения, но остаётся источником правды и местом ручных поправок.

Светофор, средний темп и анти-тишина обслуживают основной сценарий. Их нельзя превращать в дополнительную ручную работу ответственного.

### Критерий продуктового успеха

Студенту не нужно писать сообщение, чтобы занять номер. Ответственному не нужно сопоставлять чат с таблицей, чтобы понять, кто записан, кому стоит выходить и кому начислить выход. После выбора подпункта обычное подтверждение за бронировавшим выполняется одним нажатием.

## 2. Контекст

На практических занятиях по алгебре и геометрии действует относительная система оценивания, максимум — 10 баллов.

Текущий процесс: ведомость в Google Таблице обновляется вручную, запись на задачи происходит сообщениями в Telegram-чате.

Проблемы: потеря свободных подпунктов в переписке; неизвестные псевдонимы; непрозрачные приоритеты; нагрузка на ответственного; рассинхрон брони и фактической сдачи; случайный вызов преподавателем после 1–2 минут тишины; нестандартные начисления за сложные задачи.

## 3. Термины и инварианты

- **Выход** — учётная единица, засчитанная преподавателем. Обычное подтверждение сдачи даёт +1.
- **Бронь** — намерение сдавать подпункт. Сама по себе ничего не начисляет.
- **Номер** — задача, например `3.1`, объединяющая подпункты `а`, `б`, `в`.
- **Активные** — записи ведомости со статусом `Студент` или `Админ`, независимо от наличия Telegram-привязки и активности сегодня.
- **Эталон `N_max`** — максимальное число выходов среди активных.
- **Ответственный** — пользователь с ролью `Админ`.
- **Сдача** — подтверждённый ответственным факт решения конкретного подпункта конкретным человеком.

Инварианты:

1. Бронь не меняет число выходов и баллы.
2. Один студент держит не более одной активной брони; у подпункта не более одного бронировавшего.
3. Один факт сдачи не начисляется повторно при повторном callback.
4. Фактическая сдача возможна без предварительной брони и без Telegram-привязки сдавшего.
5. Очистка табло не обнуляет накопленные выходы.
6. Запись человека существует независимо от Telegram. `TG_ID` идентифицирует аккаунт, если привязка есть; ник не является ключом.
7. Таблица — источник правды. Обнаруженная ручная поправка является итогом, а старый снимок таблицы нельзя путать с новой ручной правкой.

## 4. Роли и регистрация

| Роль | Права и участие |
| --- | --- |
| `Админ` | Права студента; подтверждение сдачи; выбор другого сдавшего; одобрение привязок; снятие чужой брони; управление табло и статусами; `/sync`; `/clear` |
| `Студент` | Добавление задач в пул; бронирование и отмена своей брони после одобрения привязки; просмотр своих показателей |
| `Внесистемы` | Нет Telegram-привязки и брони в рабочем сценарии; выходы учитываются через ответственного; исключён из максимума и среднего |

Роль назначает ответственный. Это не динамическая категория светофора. Ручного управления допуском 🔴 в первой версии нет.

### Регистрация активных

1. Пользователь открывает личный чат с ботом и запускает регистрацию `/reg`.
2. Выбирает своё ФИО из ведомости.
3. Ответственный получает запрос и подтверждает либо отклоняет привязку.
4. Только одобренная привязка позволяет бронировать от имени выбранного человека.

Свободный выбор ФИО не выдаёт административные права. Нельзя одобрить двух людей на одну уже занятую запись или незаметно перепривязать её.

Незарегистрированный или ещё не одобренный пользователь при клике получает личную подсказку о регистрации/ожидании одобрения, без сообщения в общий чат.

### Внесистемные и записи без TG_ID

Их не нужно заставлять регистрироваться. Они остаются обычными строками ведомости с ФИО и выходами; `TG_ID` допускается пустым. Ответственный может выбрать такого человека в панели и засчитать ему сдачу.

Отсутствие `TG_ID` у активного студента само по себе не означает статус `Внесистемы`.

## 5. Баллы и приоритеты

### 5.1. Максимум и баллы

Для множества активных `A`:

- `N_max = max(N_i for i in A)`, если активные есть;
- `N_max = 0`, если активных нет.

При `N_max > 0`: `Баллы = ceil(10 × N / N_max)`.

При `N_max = 0`: баллы равны `0`.

`N` включает подтверждённые выходы и применённые ручные поправки. Выходы `Внесистемы` хранятся, но максимум и среднее активных не повышают.

По ожиданию владельца продукта внесистемные выходят редко и не превышают активный максимум. Отдельный пользовательский сценарий для обратного случая не требуется; прочерк вместо их баллов не утверждён. В обычном случае применяется исходная формула. Общий исходный предел — 10 баллов; численная защита не должна требовать нового ручного процесса. Граница этого ответа описана в [решениях](DECISIONS.md).

### 5.2. Светофор

Категория пересчитывается после изменения выходов, ролей и данных ведомости.

| Категория | Условие | Смысл |
| --- | --- | --- |
| ⚪ Вне системы | Роль `Внесистемы` | Не участвует в брони, максимуме и среднем |
| 🟢 Приоритет — стартовое исключение | Активный, `N = 0` и `N_max <= 1` | Защита от блокировки начала семестра |
| 🔴 Эталон | Активный, `N = N_max`, если не сработало стартовое исключение | Бронирует только после автоматического допуска |
| 🟡 Резерв | Активный, `N = N_max - 1`, если не сработало стартовое исключение | Допускается после окна 🟢 |
| 🟢 Приоритет | Активный, `N <= N_max - 2` | Имеет первое окно бронирования |

Открытие доступа не меняет категорию человека: 🔴 остаётся 🔴, но временно может бронировать.

### 5.3. Средний темп

`N_avg_active = sum(N_i for i in A) / len(A)`; при пустом `A` среднее равно `0`.

На табло выводятся среднее и максимум. `Внесистемы` не учитываются. Среднее — выбранная метрика темпа, а не точный тест доли участников у максимума.

### 5.4. Окно 🟢 и автоматический допуск 🔴

1. После добавления новых задач сначала действует окно **20 секунд только для 🟢**.
2. Во время окна 🟡 и 🔴 ждут, включая 🔴 с выполненным плановым порогом.
3. Если нет зарегистрированных 🟢, способных взять бронь, окно пропускается.
4. Затем 🟡 могут бронировать.
5. 🔴 допускаются автоматически при выполнении хотя бы одного условия:
   - `N_max - N_avg_active <= BENCHMARK_RAISE_DELTA`, исходное значение `0.5`;
   - прошло `SILENCE_TIMEOUT` секунд после публикации новых задач или последней успешной брони, исходное значение `60`.

Новая успешная бронь запускает отсчёт анти-тишины заново. Если плановый порог при этом не выполнен, допуск, основанный только на истечении таймера, закрывается. Плановый допуск зависит от текущих показателей.

**Ручного лока, разблокировки или тумблера нет.** Ответственный не должен следить за этим вручную. Ограничения записи не запрещают ответственному засчитать реальную сдачу любого человека.

## 6. Интерфейс и сценарии

### 6.1. Общее табло бронирования

Одно редактируемое сообщение в группе показывает:

- свободные, занятые и сданные подпункты;
- ФИО бронировавших;
- `N_avg_active` и `N_max`;
- текущий этап доступа к записи.

Одна кнопка соответствует одному номеру, а не каждой букве. Когда свободных подпунктов нет, кнопка помечается `🔒`. Подпись должна явно позволять понять, сколько букв свободно; конкретную компактную раскладку определяет UI-проектирование.

Подтверждения сдачи и административные рабочие кнопки находятся в личной панели, а не в общем табло.

### 6.2. Добавление и уведомление

`/add 3.1 а б` создаёт номер с подпунктами. `/add 3.1 в г` добавляет новые буквы к тому же номеру, сохраняя существующие брони и факты сдачи. Повтор буквы не создаёт дубликат.

На новую порцию задач — **один общий пинг приоритетным**. Повтор команды без новых подпунктов и обычные клики не должны порождать серию пингов. Личные уведомления каждому 🟢 не являются выбранным вариантом.

### 6.3. Бронирование

1. Студент нажимает кнопку номера.
2. Бот проверяет одобренную привязку, роль, свою текущую бронь и текущий этап допуска.
3. Назначает первую свободную букву: `а → б → в`.
4. Обновляет табло и лично отвечает через `answerCallbackQuery`.

Повторное нажатие номера со своей бронью снимает её. Если занято другое задание, новая бронь не создаётся: показывается личное напоминание.

Успех, запрет и ошибки клика не публикуются отдельными сообщениями в группу.

### 6.4. Личная админ-панель

Ответственный один раз запускает бота в личке. В панели доступны задачи и подпункты, ФИО бронировавшего, его выходы, баллы и категория, подтверждение сдачи и выбор другого сдавшего.

Обычный путь: выбрать подпункт → `✅ Сдал [ФИО бронировавшего]`.

При подтверждении:

1. Подпункт отмечается сданным за фактическим сдавшим.
2. Ему начисляется +1 выход; с другим весом работают через правку итогового числа в таблице.
3. Его остальные активные брони снимаются.
4. Пересчитываются показатели и категории, обновляются обе рабочие зоны, ставится задача синхронизации.

Если сдал другой человек, действие `🔄 Сдал другой` открывает список ФИО. Активные сортируются от 🟢 к 🔴; внесистемные и люди без Telegram-привязки также должны быть доступны для учёта факта, а не для записи в очередь.

Пример: Иванов занял `3.2 а`, Петров — `3.4 б`, но `3.2 а` сдал Петров. Выход получает Петров, `3.2 а` закрывается, Иванову ничего не начисляется, бронь Петрова на `3.4 б` снимается.

### 6.5. Отмена брони, ошибка подтверждения, конец пары

- Ответственный может снять чужую бронь.
- `/clear` очищает текущее табло и брони, не меняя накопленные выходы.
- Незавершённая бронь ничего не начисляет.
- Старые кнопки не воздействуют на новую сессию после очистки.
- **Отдельной отмены сдачи в первой версии нет.** Ошибочный счётчик исправляется в таблице; статус подпункта от этой правки автоматически не восстанавливается.

### 6.6. Команды и действия

| Команда / действие | Назначение |
| --- | --- |
| `/reg` | Выбор ФИО и запрос подтверждения привязки |
| `/add 3.1 а б` | Создание номера или добавление подпунктов |
| `/me` | Собственные выходы, баллы, роль и категория |
| Кнопка номера | Бронь первой свободной буквы / отмена своей брони этого номера |
| Одобрить / отклонить привязку | Разовое действие ответственного в личке |
| `✅ Сдал [ФИО]` | Подтверждение фактической сдачи в личной панели |
| `🔄 Сдал другой` | Выбор сдавшего из ведомости, в том числе без TG_ID |
| `🗑 Снять бронь` | Административная отмена брони |
| `/sync` | Немедленная попытка синхронизации |
| `/clear` | Очистка текущего табло без обнуления ведомости |

## 7. Ведомость, хранение и синхронизация

### 7.1. Логические поля

| Поле | Назначение |
| --- | --- |
| `ФИО` | Имя человека в ведомости и интерфейсе |
| `TG_ID` | Необязательная одобренная связь с аккаунтом Telegram |
| `Статус` | `Админ`, `Студент`, `Внесистемы` |
| `Выходы` | Накопленный счётчик |
| `Баллы` | Производное значение |
| `Категория` | Производный светофор |

Точная вкладка и физическая схема проверяются до подключения реальной таблицы. Обязательная дополнительная колонка ID не утверждена. Внутренняя идентификация записей не должна требовать регистрации внесистемных.

ФИО, статус и выходы может править ответственный в таблице. Ручная правка баллов и категории не является способом управления расчётами.

### 7.2. Источник правды

**Google Таблица имеет приоритет.** Обнаруженное ручное число — готовый итог, уже учитывающий выходы; к нему нельзя автоматически добавлять тот же ожидающий отправки +1.

Это не означает безусловно принимать любой старый снимок таблицы во время debounce. Нужно различать ещё не отправленную локальную сдачу и обнаруженное внешнее изменение. Детали алгоритма и ограничения API описаны в [технических заметках](IMPLEMENTATION_NOTES.md).

Новый ручной процесс выбора стороны конфликта и обязательный отдельный журнал поправок не выбраны.

### 7.3. Оперативное состояние

RAM + локальный `state.json`, валидация Pydantic v2, атомарная запись через временный файл и `os.replace`, защищённые изменения через `asyncio.Lock`.

Нужно сохранять задачи, брони, одобренные и ожидающие привязки, данные ведомости и ожидающие синхронизации изменения. Сетевые запросы не должны удерживать весь интерфейс под общим замком.

### 7.4. Push / Pull

- Push: изменения выходов, статусов и одобренных привязок; производные поля после пересчёта.
- Debounce Push: 1.5 секунды, пакетная запись.
- Pull: каждые 30 секунд и по `/sync`.
- Результат Pull пересчитывает максимум, среднее, баллы, категории и обновляет обе рабочие зоны.
- Само бронирование не меняет выходы и не требует записи этого счётчика в таблицу.
- Сбой API не должен выдаваться за успешную синхронизацию; ожидающие изменения должны переживать перезапуск.

### 7.5. Корректировки

За сложный номер могут засчитать два выхода. В первой версии ответственный корректирует итоговое число в таблице, после чего Pull или `/sync` переносит результат в бот.

Встроенный редактор веса, отдельный лист событий поправок и кнопка отмены сдачи в текущую договорённость не входят.

## 8. Планируемая архитектура и запуск

Python 3.11+, aiogram 3.x, gspread-asyncio, Pydantic v2.

```text
algem-bot/
├── main.py              # Поллинг Telegram и фоновые задачи
├── config.py            # Настройки и ссылки на секреты окружения
├── models.py            # Люди ведомости, привязки, задачи и состояние
├── engine.py            # Расчёты, окно 🟢 и автоматические права брони
├── storage.py           # Чтение, атомарная запись и защита состояния
├── sheets_sync.py       # Push/Pull и приоритет внешних поправок
├── workers.py           # Таймеры и периодическая синхронизация
└── handlers/
    ├── student.py       # Выбор ФИО, задачи, бронь, /me
    └── admin.py         # Личная панель, одобрение, сдача, /sync, /clear
```

Это предлагаемая структура будущего кода, а не уже созданная реализация.

Настройки: `BOT_TOKEN`, `SHEET_ID`, путь к ключу сервисного аккаунта, `GREEN_WINDOW_SECONDS=20`, `SILENCE_TIMEOUT=60`, `BENCHMARK_RAISE_DELTA=0.5`, Pull 30 секунд, debounce 1.5 секунды.

Хостинг не выбран. На этом этапе не настраиваются сервер и платные сервисы; инструкции локального запуска появятся с кодом. Для JSON-хранилища требуется один экземпляр бота и сохраняемый диск; многопроцессный запуск не обеспечивается одним `asyncio.Lock`.

| BL-05 | Аналитика | Среднее активных и плановый допуск 🔴 по разрыву с максимумом | Высокий |
| BL-06 | Учёт | Личная админ-панель: сдача и выбор другого сдавшего, включая внесистемных без TG_ID | Высокий |
| BL-07 | Интеграция | Push/Pull; таблица — источник правды и приоритет ручных итогов | Высокий |
| BL-08 | Гибкость | Ручные поправки выходов и ролей через таблицу | Средний |

Главный реализационный путь: «добавить → занять → увидеть ФИО и показатели → подтвердить → автоматически обновить учёт». Из BL-04 исключено ручное управление, ранее бывшее частью исходного ТЗ.

## 10. Критерии приёмки

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| AC-01 | Запись на свободный номер | Первая свободная буква закрепляется за студентом, табло обновляется, результат приходит лично |
| AC-02 | Подтверждение за бронировавшим | В личной панели уже известны ФИО и показатели; после выбора подпункта достаточно одного подтверждения |
| AC-03 | Начало семестра | При `N_max=0` баллы равны 0; при `N_max<=1` активные с 0 выходов имеют 🟢; деления на ноль нет |
| AC-04 | Сдал другой человек | Правильный подпункт закрыт за реальным сдавшим; старому бронировавшему ничего не начислено; другая бронь сдавшего снята |
| AC-05 | Добавлены новые буквы | Старые буквы, брони и факты сдачи сохранены; дубликатов нет |
| AC-06 | Два клика на последнюю букву | Бронь получает только один; второму — личный ответ о занятости |
| AC-07 | Pull вернул прежний снимок во время debounce | Свежий локальный выход не теряется только из-за ещё не завершённого Push |
| AC-08 | Обнаружена ручная поправка того же счётчика | Итог из таблицы имеет приоритет, уже учтённый локальный +1 повторно не прибавляется |
| AC-09 | Бронь не успели сдать | Отмена или `/clear` ничего не начисляет и не меняет накопленные выходы |
| AC-10 | Нет одобренной привязки | Личная подсказка о регистрации/ожидании одобрения, бронь не создаётся |
| AC-11 | Все записи `Внесистемы` | Максимум и среднее равны 0, ошибок нет; ответственный всё ещё может учитывать факты их сдачи |
| AC-12 | Попытка второй брони | Вторая не создаётся; показано напоминание о текущей |
| AC-13 | Повторное нажатие своего номера | Бронь отменена, счётчик не изменён |
| AC-14 | Повторный callback сдачи | Начисление не дублируется |
| AC-15 | Обычные клики | Не создают служебных сообщений в группе; на порцию новых задач не более одного общего пинга |
| AC-16 | Google API недоступен | Оперативные действия не зависают на сетевом запросе; ожидающая отправка сохраняется, ложного успеха синхронизации нет |
| AC-17 | Не-Админ вызывает админское действие | Сервер отклоняет действие, состояние не меняется |
| AC-18 | Старое табло после `/clear` | Старая кнопка не влияет на новую сессию |
| AC-19 | Первые 20 секунд при доступных 🟢 | 🟢 бронируют; 🟡 и 🔴 получают личное объяснение ожидания |
| AC-20 | Нет зарегистрированных 🟢, способных взять бронь | Окно 🟢 пропускается; 🟡 не ждут искусственно |
| AC-21 | Внесистемный без Telegram сдал задачу | Ответственный выбирает его ФИО, выход учтён; `N_max` и среднее активных не меняются |
| AC-22 | Два запроса привязки к одному ФИО | Нельзя одобрить обе привязки или перезаписать первую незаметно |
| AC-23 | Повторная команда без новых букв | Не создаёт дубликаты и дополнительный пинг о якобы новой порции задач |

## 11. Границы версии

Не входят: веб-приложение, распознавание старого чата, самостоятельное подтверждение сдачи студентом, ручной лок 🔴, отдельный журнал корректировок, встроенная отмена сдачи, мультигрупповая SaaS-платформа и постоянный хостинг как уже настроенная услуга.

В этой версии репозитория только документация и `.gitignore`. Код и тесты ещё не написаны; интеграции Telegram/Google не подключены. Решения контрольных вопросов не означают, что уже настроены секреты и среда запуска.
