# Технические заметки и открытые вопросы

**Версия:** 0.1 от 19 ноября 2026 года.  
**Связанный документ:** [спецификация продукта](SPEC.md).

Этот файл отделяет обязательные свойства решения от ещё не согласованных способов их реализации. Технические предложения ниже не следует выдавать за решения, уже утверждённые владельцем продукта.

## 1. Зафиксированные продуктовые ориентиры

1. Главный результат — простая запись студентов на номера и меньше ручной работы у ответственного.
2. Табло — основной рабочий интерфейс пары; таблица не должна быть обязательным вторым экраном для обычного подтверждения сдачи.
3. Роль, показатели и ФИО должны быть доступны без сопоставления переписки с ведомостью.
4. Бронь не является выходом. Основание для обычного начисления — подтверждение Админа.
5. Светофор и анти-тишина помогают этому процессу, но не должны усложнять обычное действие.

## 2. Конкурентность: исправление исходного допущения

Однопоточный `asyncio` не означает, что обработчики Telegram исполняются целиком последовательно. На `await` другой обработчик или воркер может изменить состояние. Поэтому полагаться на сам факт использования `asyncio` для защиты последней буквы нельзя.

Обязательный результат:

- проверка доступности и закрепление подпункта образуют одну защищённую транзакцию;
- проверка прав, текущей брони и изменение состояния используют согласованный снимок;
- подтверждение конкретной сдачи идемпотентно;
- административная передача сдачи выполняется целиком, а не несколькими независимыми изменениями.

Предлагаемая реализация:

1. Захватить `state_lock`.
2. Проверить актуальные права и состояние.
3. Выполнить все связанные изменения.
4. Надёжно сохранить новое состояние и пометить нужные изменения для синхронизации.
5. Освободить блокировку.
6. Выполнить Telegram/Google I/O отдельно.

Длительное удержание общего state-lock на сетевых запросах будет блокировать бронирование. Для сетевой синхронизации целесообразна отдельная координация, а не один глобальный замок на весь бот.

## 3. Push/Pull: исправление исходной гарантии

Один `Lock` вокруг запросов к Google API сам по себе не защищает от логически устаревших данных.

Пример:

1. В таблице и локально у студента 5 выходов.
2. Админ подтверждает сдачу; локально становится 6.
3. Push ждёт окончания debounce 1.5 секунды.
4. Pull успевает прочитать из таблицы 5.
5. При безусловном применении Pull локальная 6 будет потеряна, даже если операции формально сериализованы.

Кроме того, администратор редактирует таблицу вне локального `asyncio.Lock`, и этот замок не контролирует его действия.

### Необходимые свойства

- Различать синхронизированное состояние и ожидающие отправки локальные изменения.
- Не считать отсутствие строки в очередном ответе API разрешением удалить пользователя или обнулить его результаты.
- Не снимать признак ожидающей отправки, если во время запроса возникла новая локальная ревизия.
- После перезапуска знать о неотправленных изменениях.
- Не затирать молча правки, которые одновременно появились с двух сторон.
- Не объявлять `/sync` успешным при фактическом сбое API.

### Предлагаемое направление, не утверждённый алгоритм

- Сохранять последнюю общую версию полей, локальные ревизии и устойчивый список ожидающих отправки изменений.
- Разделять изменения по пользователю и полю, чтобы правка ФИО не конфликтовала с независимым начислением выхода.
- Сериализовать циклы синхронизации отдельно от коротких транзакций оперативного состояния.
- Если локальное поле не менялось, принимать обнаруженную внешнюю правку.
- Если есть локальная правка, а таблица ещё содержит последнюю общую версию, не откатывать локальное состояние.
- Если обе стороны изменили одно поле по-разному, считать это конфликтом и применять явно согласованную политику, а не произвольный last-write-wins.

Запись абсолютных счётчиков в редактируемые человеком ячейки не является транзакционной БД. Без дополнительного протокола нельзя обещать полное отсутствие конфликтов при любых одновременных ручных правках. Конкретную политику необходимо выбрать до реализации BL-07.

## 4. Надёжность и безопасность реализации

Следующие детали следуют из необходимости корректно выполнять основной сценарий:

- Стабильный идентификатор пользователя — `TG_ID`; ник и положение строки в таблице не являются ключами.
- Полномочия проверяются в обработчике каждого административного действия, а не только наличием кнопки.
- Баллы лучше считать целочисленно: при `N_max > 0` значение равно `(10 * N + N_max - 1) // N_max`.
- Значения выходов должны валидироваться как неотрицательные целые числа; повреждённая строка не должна молча становиться нулём.
- Для старых callback после `/clear` нужен способ отличать прежнюю сессию/версию табло от текущей.
- Конкурентные перерисовки не должны откатывать табло к более старому снимку; сообщения Telegram следует обновлять согласованно и с учётом ограничений API.
- Атомарная запись JSON защищает от частично записанного файла, но сама по себе не заменяет проверку схемы, обработку ошибок диска и сохранение очереди синхронизации.
- Конкретная стратегия восстановления при повреждении файла и резервирования состояния ещё проектируется.
- Токен бота, JSON сервисного аккаунта и приватные SSH-ключи не хранятся в репозитории и не публикуются в переписке.
- Тестовые данные обезличиваются; реальные ФИО, TG_ID и ведомость не коммитятся.

| Q-02 | Где ответственный видит выходы/баллы/приоритет: в общем сообщении, в отдельной административной панели или в комбинации? | Нужно сохранить сценарий без поиска в таблице и не перегрузить общее табло |
| Q-03 | 🟡 может бронировать сразу или ждёт отдельного окна для 🟢? | В исходном ТЗ явно ограничены только 🔴; дополнительный запрет нельзя додумывать |
| Q-04 | Когда таймер тишины сбрасывается: только после успешной брони, также после сдачи или добавления подпунктов? Когда доступ 🔴 закрывается повторно? | Иначе условия доступа неоднозначны и могут неожиданно меняться на паре |
| Q-05 | Ручная разблокировка — постоянный override до отключения или одноразовое разрешение? | Определяет смысл тумблера и поведение после пересчёта |

| Q-07 | Как назначается первый Админ и ограничивается доступ участников нужной группой? | Нельзя допустить самовыдачу административных прав или регистрацию посторонних |
| Q-08 | Что делать при одновременной ручной правке и локальном изменении одного счётчика: запрос решения, приоритет стороны или иной протокол? | Нужно исключить скрытую потерю выхода или ручной поправки |
| Q-09 | Как показывать и дозировать пинг 🟢? | Основная цель продукта — уменьшить шум |
| Q-10 | Что именно значит `(1/2)` на кнопке: занято, сдано или занято вместе со сданным? | Студент должен однозначно понимать наличие свободной буквы |

| Q-12 | Как меняются существующие брони при смене роли на `Внесистемы` или изменении приоритета? Может ли Админ записать фактическую сдачу участнику `Внесистемы`? | Исключение из очереди не определяет все случаи фактического учёта |
